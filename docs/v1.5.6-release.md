# v1.5.6 — Pembatalan resi J&T dan rekonsiliasi refund

Seller dapat membuka **Batalkan resi J&T** langsung pada detail pesanan sebelum pickup dikonfirmasi kurir, termasuk setelah seller mencatat serah-terima. Pernyataan seller tetap disimpan; status perjalanan resmi tetap menentukan kelayakan pembatalan. Keputusan akhir pembatalan berasal dari respons J&T yang cocok dengan ID order aslinya.

| Before | After | Why |
| --- | --- | --- |
| Tombol pembatalan hilang setelah pernyataan serah-terima seller | Tombol terlihat sampai ada bukti paket diproses kurir | Pernyataan seller tidak sama dengan penerimaan paket oleh kurir |
| ID pesanan toko terlihat, ID order carrier tersembunyi | ID order J&T tampil dan dapat disalin di samping resi | Pembatalan memakai ID yang dikirim saat pembuatan resi, bukan nomor pesanan storefront |
| Event pembatalan carrier tersimpan sebagai riwayat saja | Tracking mengonfirmasi pembatalan secara idempoten | Perubahan melalui kanal resmi di luar dashboard dapat direkonsiliasi |
| Pesanan dengan refund penuh masih menawarkan persiapan pengiriman | Pengiriman ditahan; pesanan ditutup setelah pembatalan carrier dan refund penuh dikonfirmasi | Tidak ada instruksi mengirim barang setelah seluruh dana dikembalikan |

## Kontrak dan pengamanan

- `orderNumber` publik dan `externalOrderId` J&T tetap merupakan dua identitas berbeda. ID lama tidak diganti atau ditebak. API pembatalan mengembalikan kedua ID dan AWB; UI mengirim `expectedExternalOrderId` sebagai pengaman terhadap halaman lama, bukan pengganti ID tersimpan. Halaman lama perlu dimuat ulang.
- Respons pembatalan yang diterima harus cocok dengan ID tersimpan. Hanya respons `CANCEL_ORDER` dengan format terminal persis seperti dokumentasi resmi yang diterima sebagai acknowledgement idempoten; error lain tetap ditolak/tidak pasti. Referensi: [J&T Developer](https://developer.jet.co.id/documentation).
- Rekonsiliasi tracking memerlukan kode `162` beserta status tepat `Cancelled AWB by Seller`, identitas AWB/order yang diperiksa transport, timestamp valid, dan tidak ada event terbaru yang bertentangan. Kontrak kode/status ini diverifikasi melalui tracking read-only akun J&T Hubify. Timestamp yang sama boleh memperbaiki event yang sudah tersimpan oleh versi lama.
- Pembatalan resi sendiri tidak membatalkan pesanan, mentransfer uang, atau mengembalikan stok. Penutupan otomatis ke `CANCELLED` hanya untuk pesanan belum dikirim, pembayaran yang sudah `REFUNDED`, refund penuh yang sudah dikonfirmasi pembeli dan cocok dengan catatan transfer, semua kasus terminal, resi carrier sudah dibatalkan, serta tanpa bukti perjalanan fisik. Jalur ini hanya menulis status, riwayat dan audit; ledger refund/transfer dan inventory tetap.
- Urutan pembatalan carrier lalu konfirmasi refund, maupun sebaliknya, menghasilkan kondisi akhir yang sama. Row lock, pemeriksaan AWB/ID, deduplikasi event dan status terminal menjaga concurrency dan replay. Tracking tetap tersedia saat hasil cancel belum pasti, tanpa mengirim ulang permintaan cancel.
- Return yang benar-benar sudah dikirim tidak diubah menjadi pembatalan sebelum pengiriman. Pembuatan resi baru, serah-terima dan penyelesaian tetap diblokir selama hold finansial.
- RBAC, pemeriksaan origin, validasi payload, batas alasan, feature flag, snapshot konfigurasi terenkripsi dan protokol rekonsiliasi operator dipertahankan. Tidak ada migrasi, perubahan dependency, DNS, Email & OTP, relay, installer atau platform pusat.

## Verifikasi dan operasi

Tes mencakup respons carrier identity-matched, pembatalan berulang/tidak pasti/ditolak, race pickup dan cancel, halaman lama, pemulihan event lama, dua urutan refund, refund sebagian, return fisik, serta bukti bahwa refund/stok tidak berubah. Pemeriksaan browser memakai database lokal terpisah pada lebar 360, 390, 430 dan 1440 piksel, tanpa dispatch create/cancel ke J&T.

Verifikasi lokal: 626 tes lulus, 3 dilewati; typecheck dan build produksi lulus. Setelah penyesuaian tipe query pengujian, tiga tes UI dijalankan ulang dan lulus. Pengujian database pembatalan terakhir (18 tes) juga memeriksa akses tracking melalui service berizin saat cancel belum pasti. Browser mencatat 19 pemeriksaan lulus, 13 screenshot, nol request carrier dan nol transfer sungguhan. Lint: 0 error, 37 warning existing.

Deploy Hubify dilakukan sebagai patch kode tanpa SQL, dengan backup yang diuji restore, image rollback v1.5.5, pemeriksaan checksum migrasi, konfigurasi proxy bersama dan service lain. Rekonsiliasi pesanan live yang dilaporkan hanya boleh melalui fungsi tracking baru setelah backup dan verifikasi identitas/payment/refund; jangan membuat transfer atau restock tambahan. Jika provider tidak mengonfirmasi pembatalan, pertahankan data dan laporkan kebutuhan rekonsiliasi.

Rollback kode memakai image v1.5.5 dengan database/config terkini. Tidak mengembalikan database lama atau menghapus catatan pembatalan/refund. Hasil pemeriksaan final dan deployment dilaporkan terpisah beserta SHA rilis.
