# Kandidat v1.0.1: progres wizard dan pemeriksaan update

## Penyebab wizard terlihat macet

v1.0.0 hanya mengirim `busy` dan pesan umum. `initialize_store` menunggu Docker build
selesai sebelum menulis `built`. Polling dua detik berfungsi, tetapi tidak memiliki
checkpoint untuk ditampilkan. Build panjang terlihat macet meskipun backend bekerja.

v1.0.1 menyimpan fase, status dan timestamp dalam `setup.json` root-only:

1. Verifikasi ulang domain dan HTTPS.
2. Pemeriksaan Docker/Compose dan penyiapan konfigurasi.
3. Build image aplikasi/tools, termasuk dependensi dan Next.js.
4. PostgreSQL sehat.
5. Migrasi database.
6. Pembuatan/pemulihan admin sekali saja dan hak runtime.
7. Aktivasi app dan rute Caddy.
8. Readiness lokal serta storefront/login/HTTPS.
9. Metadata versi, maintenance timer, konfigurasi akhir dan pencabutan token setup.

Docker dipasang oleh install.sh sebelum wizard; fase kedua memeriksa kesiapannya.
Checkpoint selesai hanya setelah operasi terkait berhasil. Bar menunjukkan jumlah
checkpoint, bukan persentase waktu. Build aktif memakai indikator indeterminate.
Proyeksi API hanya mengizinkan ID/label/status/timestamp; tidak mengirim password,
setup token/hash, server challenge atau environment.

Refresh dan putusnya SSH tidak menghentikan service systemd. Setelah service/server
restart, fase yang ditinggal berjalan ditandai terputus dan menawarkan finalisasi
ulang. Checkpoint selesai, secret dan admin existing dipertahankan. Gangguan polling
menampilkan masalah koneksi, bukan mengklaim build gagal. Tahap Selesai tetap
menunggu health check final dan konfigurasi berhasil.

## Audit updater dan batas dashboard

v1.0.0 mempunyai CLI, tanpa halaman/API dashboard tersembunyi yang belum tersambung.
`update.sh` memerlukan root dan `flock` operasi toko. `/etc/single-store/version.json`
mencatat versi/source SHA/kontrak/inventory migrasi. Updater memverifikasi repository
ID, stable release, tag/commit, digest GitHub, seluruh checksum file dan migrasi.
Paket/kompatibilitas diperiksa sebelum konfirmasi; setelah itu penulisan dihentikan,
DB/media/config dibackup, lalu build terpisah, migrasi, aktivasi dan health check.
`update.json` menyimpan journal recovery. Pemulihan kode/container mempertahankan
skema additive; tidak mengklaim rollback database penuh.

Halaman baru: **Pengaturan → Pembaruan Aplikasi**, `/admin/settings/updates`.
Versi terpasang berasal dari package image aplikasi yang sedang berjalan, sehingga
mengikuti aktivasi/rollback tanpa memasang file konfigurasi root ke web. GET membaca
snapshot; POST pemeriksaan memerlukan sesi aktif, role Admin, izin database
`audit.read` dan Origin yang cocok. Tidak perlu migrasi permission/akun existing.

Pembaca rilis hanya memakai endpoint HTTPS GitHub resmi yang konstan. Repository
ID/nama, rilis stable, tag terurai ke commit, URL/nama/ukuran asset dan digest
divalidasi. Redirect ditolak; metadata dibatasi 1 MiB dan timeout per request 10 detik.
Request tidak menerima URL, versi, path, shell atau operasi apply. Changelog berupa
teks biasa. Pemeriksaan paralel ditolak 409; interval minimum 30 detik per proses.
Snapshot sementara hilang saat restart dan dapat diperiksa kembali.

Status membedakan belum diperiksa, release belum ada, versi sama, tersedia versi
baru, dan aplikasi lebih baru daripada release stabil. Tidak ada versi fiktif.
Kompatibilitas tetap memerlukan pemeriksaan paket/database oleh CLI; metadata saja
tidak cukup untuk menyatakan paket aman diterapkan pada database toko ini.

**P3 ditunda mengikuti fallback aman yang diminta.** Belum ada worker lokal dengan
protokol allowlist, autentikasi antarproses, izin eksekusi khusus dan hardening systemd
yang terbukti aman untuk menerima permintaan web. Next.js tetap non-root tanpa
Docker socket, sudo atau konfigurasi root. Tidak ada tombol Update Sekarang maupun
endpoint eksekusi shell. Update/backup/recovery yang diuji tetap memakai CLI nyata.

Sebelum P3 diaktifkan diperlukan service lokal terbatas, otorisasi tahan replay,
permission eksekusi khusus, lock bersama CLI, konfirmasi/audit actor, journal/status
tanpa secret serta uji privilege escalation, interupsi dan pemulihan ketika aplikasi
web dihentikan. Memberikan socket Docker atau sudo ke Next.js bukan jalurnya.

## Validasi dan operasional

Unit test memeriksa checkpoint saat operasi berjalan, kegagalan/restore, proyeksi
tanpa secret, urutan operasi dan health check gagal; serta release sama/lebih baru,
identitas/tag/digest tidak valid, jaringan, metadata besar, CSRF, role dan paralelisme.

CI menginstal kandidat pada runner Ubuntu 24.04 dan guest Ubuntu **2048 MiB RAM,
2 vCPU, swap 2 GiB**. Browser menangkap progress build desktop/mobile, refresh saat
build, recovery, selesai dan halaman update. Dashboard memeriksa release GitHub
nyata. Kasus release sama/lebih baru memakai unit fixture; tidak ditampilkan sebagai
release resmi. CLI memakai dua paket disposable sesudah kandidat: sukses additive,
backup/scratch restore, lalu kegagalan aktivasi dan pemulihan kode dengan
admin/brand/produk/stok/media/config tetap utuh. Artifact CI menyimpan hasil,
screenshot dan pengukuran RAM/swap/build/OOM.

Jalankan lint, typecheck, unit test dan CI integrasi. Lint seluruh src memakai Next
core-web-vitals; warning img lama pada hero editor tidak diubah di luar scope.
Build Docker/Next berada di guest 2 GB, terpisah dari RAM browser di host.

Recovery instalasi: jalankan installer dengan SHA/mode yang sama, buka tunnel dan
lanjutkan finalisasi. Recovery update: `sudo bash update.sh --recover` dari clone.
Uji backup tanpa menimpa DB aktif: `sudo bash restore.sh --check PATH_BACKUP`.
Lihat operations.md dan updates.md untuk prosedur serta batas rollback database.

Tidak memasang kandidat, mereset/memigrasi atau menguji destruktif Tencent live,
hubify.web.id maupun gheverhan.store. Tidak membuat tag/release/merge v1.0.1 atau
mengaktifkan J&T Production. Kontrak database tetap; tidak ada migrasi bisnis baru.
