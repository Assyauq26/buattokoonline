# v1.8.3 — Konfirmasi blu otomatis dan QRIS merchant

## Perubahan untuk seller dan customer

- blu: alasan kesiapan ditampilkan sebelum aktivasi. Setelah seller mengaktifkan
  mode otomatis, satu notifikasi dana masuk blu yang tervalidasi, rekening sesuai,
  nominal tepat dan batas waktu valid dapat melunasi satu pesanan secara otomatis.
  Nama pengirim tidak digunakan untuk pencocokan. Alur pesanan lama dipertahankan.
- QRIS GoPay Merchant: hubungkan melalui OTP di dashboard, periksa merchant,
  unggah PNG/JPEG/WebP atau payload QRIS statis, lihat preview, lalu aktifkan.
  Integrasi ini tidak resmi dan dapat terdampak perubahan layanan penyedia.
- Customer mendapat nominal akhir berkode unik, countdown, salin nominal/rekening,
  QRIS/unduhan gambar dan cek pembayaran, tanpa unggah bukti untuk kedua metode
  otomatis. Status lunas hanya berasal dari backend.
- Worker backend memakai lease/cooldown bersama, sesi terenkripsi, refresh/retry
  terbatas, cursor mutasi persisten dan klaim transaksi permanen. Pembayaran dapat
  diperiksa walaupun tab ditutup. Mutasi refund, pending, gagal, tidak dikenal,
  ambigu, terlambat atau pesanan tertutup tidak dipaksakan menjadi lunas.
- Transfer manual tetap tersedia. Metode otomatis gagal secara eksplisit dan
  tidak diam-diam mengganti metode atau nominal pesanan yang sudah diterbitkan.

## Rollback and recovery

Pre-SQL failure with exact old ledger and no SQL intent: reconcile through the
official helper to restore only app/ingress/workers. Old code rollback after SQL
is not supported because source activation and automatic settlement semantics
changed. Keep the fence if migration/ledger is uncertain.

After committed34 with traffic still fenced: verify the new ledger/schema/data,
then reconcile forward with the same source/digest. Do not replay migration or
restore an old binary. After traffic may have opened: adopt only verified healthy
new code, finish metadata/ingress/workers; never recheck old row snapshots or
restore pre-cutover data over new orders. Fix code forward if readiness fails.

For a proven failed/incomplete migration, first verify external Docker/SQL work
has stopped, inspect journal and ledger read-only and preserve backup/fence.
Restore database only after an explicit incident decision establishes that no
new transactions will be lost and reconciles any external credits/webhooks.
Database restore is separate from application rollback and never automatic.

Runtime triggers for intervention include failed readiness, unexpected schema/
ledger/config changes, repeated provider-auth failures, duplicate/conflicting
claims, stock transaction errors or elevated HTTP failures. Disable the affected
source through its authorized setting if needed; claims/history are retained.

## Provider readiness and operator limits

GoPay endpoint/request shapes were compared with readable history and traced
under networkless mocks from current upstream. No obfuscated dependency is
installed or run with real credentials. This is not proof of live provider
acceptance. Seller must request/enter their own OTP after deployment and use their
own merchant QRIS. Missing/changed challenge/token/expiry/profile/transaction
contracts fail with a specific message and cannot fabricate a successful session.

Hubify's existing Google client/session/enrollment remain private and unchanged.
blu must be freshly read and explicitly activated for automatic new checkouts.
The per-attempt `BLU_AUTOMATIC_ATTEMPT` receipt is written in the same locked
checkout transaction after opt-in, avoiding clock comparisons or legacy changes.
Other stores require their own approved configuration/enrollment and account
connections; publication never copies Hubify credentials or enables their sources.

Live payment testing is performed by the owner after deployment. The release
does not claim a connected live GoPay account or a verified live merchant payment
until those actions actually succeed. Application expiry does not guarantee that
a previously generated QR becomes unscannable at the provider.
