# v1.9.1 — pengaman rotasi key Midtrans

Patch atas v1.9.0. GET Status memakai konfigurasi asli attempt dan dapat mencoba
key pengganti pada Merchant ID/environment yang sama setelah401. Namun404 dari
key pengganti tidak membawa identitas merchant dan tidak boleh membuktikan
ketiadaan pembayaran. Kondisi ini kini menahan rekonsiliasi/pelepasan stok,
bukan menutup order yang mungkin sudah dibayar. Status sukses tetap memerlukan
kecocokan Merchant ID, order_id, transaction_id, nominal dan currency.

Tidak ada migrasi baru:35 checksum dan schema35 tetap sama. Jalur publik memakai
mekanisme same-schema resmi dari canonical v1.9.0; rollbackCompatible=true hanya
untuk patch dengan schema identik ini. Rollback ke v1.8.3 tetap tidak diotorisasi.
Jalur Hubify memverifikasi baseline v1.9.0, pasangan historis CRLF/LF secara
read-only, semua row hash, worker guard baru, backup/restore, image dan manifest.
Stage migrasi adalah pemeriksaan no-op terhadap35 ledger/schema yang identik.
Tidak ada SQL, ledger atau metadata baseline yang dipalsukan.

Interupsi sebelum stage verifikasi mengikuti rollback sebelum migrasi resmi;
sesudahnya gunakan reconcile forward sesuai journal. Jangan restore database
lama setelah traffic baru masuk. Kunci, token, inbox dan attempt harus tetap
tersedia. Konfigurasi J&T dan koneksi pembayaran lama tidak diubah.

Review TypeScript/ESLint dan build resmi diperlukan; sesuai instruksi pemilik,
tidak menjalankan dev server, suite tes lokal, simulator atau transaksi sandbox.
Pascadeploy gunakan pemeriksaan nontransaksional yang sama. Pembayaran live
dilakukan pemilik setelah memasukkan key; tidak diklaim sudah diuji operator.

Panduan [Midtrans live](midtrans-live-guide.md) tetap berlaku. Gunakan v1.9.1
sebelum mengaktifkan merchant atau merotasi key. Artefak/tag v1.9.0 tidak ditimpa.

REST pembuatan pesanan memakai pilihan metode yang sama dengan server action
checkout: Midtrans tidak memerlukan rekening manual. Metode tidak dikenal/field
asing ditolak; JSON dibatasi64KB dan mutasi wajib same-origin. Pemilihan Midtrans
tidak boleh dibuang oleh parser API lalu diam-diam menjadi transfer manual.

Sebelum expiry, rekonsiliasi mencakup attempt sebelumnya dalam sweep terbatas.
Attempt terakhir saja tidak membuktikan attempt lama belum dibayar. Jika sweep
belum selesai atau status belum pasti, reservasi tetap ditahan dan dicoba lagi.
