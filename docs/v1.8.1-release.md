`VERSION` remains the authoritative application version. This patch is prepared
for a seller-initiated update from canonical v1.8.0; it does not start an update
on Gheverhan. Final source/digest are recorded in the immutable release manifest
and SHA256SUMS attached to the GitHub release.

## Schema and compatibility

New migration: `20261113120000_order_customer_list_index`.

```sql
CREATE INDEX "Order_userId_createdAt_id_idx" ON "Order"("userId", "createdAt", "id");
```

SQL SHA256: `ee0d01eb42e4c4a71c5d64b26e2af46ecbe79915f68f2543ff7c8e99fb538e80`.
Prisma adds the matching `@@index([userId, createdAt, id])`. The original 30 SQL
files match the published v1.8.0 archive byte-for-byte; no historical SQL/ledger
is edited. The existing additive grammar accepts this exact nonunique index.

This release is genuinely rollback-compatible with **v1.8.0 only**: a nonunique
index adds no field/constraint or transaction rewrite, and the old application
ignores it. Therefore the NEW v1.8.1 policy is true, exact installed range 1.8.0,
DB contract 1, PostgreSQL 16. The published v1.8.0 false policy and its v1.7.4
migration path remain unchanged. This does not authorize v1.7.x -> v1.8.1.

The operator publisher now derives minimum worker from the authenticated package
(`VERSION = 3`), rather than assigning worker 2 to every ordinary release.
Platform PR #15 updates only that publisher. Signature, trust, checksum, history,
backup, resource, source, J&T/unknown-request, fencing and recovery guards remain
required. The normal additive updater path executes Prisma once after fencing;
no new executor or exception to the historical-migration rules is introduced.

CREATE INDEX takes a write-conflicting table lock, so it runs in the existing
drained/fenced maintenance window. On the 1,000-order disposable fixture the
whole Prisma tool invocation took about 1.3 seconds; this is not an estimate for
every seller's database size. Resource/backup guards still apply.

The fresh installer now places the authenticated setup source SHA into app
compose metadata; invalid source identity is refused. Existing runtime secrets
and published v1.8.0 bytes are untouched.

## Seller test and recovery

After official catalog publication, the owner opens Gheverhan seller settings,
presses **Cek pembaruan**, verifies v1.8.1, then presses **Update sekarang**.
The agent does not press Update sekarang or alter the active shop's DB for this
test. A check-only preflight may be run to verify eligibility without a job.

Backup must be verified through scratch restore by the existing worker before
app activation. Application rollback can keep the added index and migration row;
do not claim schema rollback or restore an old DB after new orders. Partial SQL,
unknown daemon/carrier results or failed readiness remain recovery-required as
implemented. Retain the backup/journal and use official reconciliation; never
rewrite ledger checksums or force a failed package.
