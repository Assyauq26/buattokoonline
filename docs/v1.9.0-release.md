# v1.9.0 — Midtrans Snap

Seller dapat mengatur gateway Midtrans resmi melalui Pengaturan → Metode
Pembayaran → Midtrans. Pembeli memilih kanal merchant melalui Snap tanpa kode
unik tambahan atau unggah bukti. Webhook, worker, dan tombol Cek pembayaran
menggunakan rekonsiliasi backend yang sama.

Transfer manual tetap tersedia. Koneksi dan histori blu/GoPay lama dipertahankan
untuk order lama; pesanan otomatis baru diarahkan ke Midtrans setelah aktivasi
seller. Tidak ada aktivasi gateway atau pembaruan massal toko.

## Metadata dan gate

Sumber versi resmi adalah `VERSION`, bukan versi private package npm aplikasi.
Versi minor 1.9.0 menandai kemampuan gateway baru, dari baseline rilis publik
v1.8.3/f48f2a5f637c50537af96474e51ea4cf18948274. Artefak historis tidak ditimpa.
Manifest resmi dibuat `installer/release.py` dari commit hasil merge yang bersih.
Identitas commit, artefak, image dan bukti live dicatat pada laporan deployment.

- Baseline schema34: `b88c7c76aee2cea2a6723292c861383843c5d609a7b5187d9a9b5fa76a551a91`.
- Migrasi baru: `20261115160000_midtrans_snap`, SHA256
  `c1c0e01ec2c403e073b361ff54534ab96f1d4cebe5af7520db53b48c8716b5ee`.
- Schema35 yang diharapkan:
  `882d3a6ecc33a66a68502e630fb7d401eabf3d86828fc0ac5d570ced5ed2f78f`.
- Seluruh 34 SQL historis dan ledger existing harus tetap identik.
- Empat tabel tambahan; tidak ada perubahan harga, order, stok, promosi atau
  histori existing. FK ke Payment bersifat RESTRICT agar attempt tidak hilang.
- Partial unique index menjamin satu attempt terbuka per Payment; identitas
  transaksi provider unik, Order→Payment locks melindungi settlement tepat sekali.

Review schema dilakukan pada scratch database di PostgreSQL existing dengan
schema-only restore, tanpa layanan staging atau pembayaran simulasi. PostgreSQL
deparse empat CHECK varchar-array historis berbeda setelah dump/restore. Karena
itu hash schema hasil restore tidak diadopsi sebagai baseline. Semua objek lama
di scratch dibandingkan sebelum/sesudah, dan proyeksi tepat empat tabel baru
digabung dengan katalog schema aktual. Full schema hash aktual tetap wajib
sesudah migrasi. Tidak ada perubahan CHECK/SQL/ledger lama agar gate lolos.

Sesuai instruksi pemilik, dev server, suite tes lokal, simulator, dan transaksi
sandbox **tidak dijalankan**. Review statis TypeScript/ESLint, review alur dan
migrasi, build resmi, backup/restore verification, serta smoke nontransaksional
menjadi bukti yang dicatat. Hasil transaksi production menunggu pemilik memasukkan
key dan membayar sendiri; tidak boleh diklaim hanya karena halaman tampil.

## Runbook deployment dan recovery

1. Autentikasi commit final, exact baseline artifact v1.8.3 SHA
   `eb850edf418b4a88de7a9a7c066d6016713d1aa847216088e416daea2a0e438a`,
   tree sumber, inventori runtime, 34 checksum, schema, kapasitas dan lock.
2. Update worker melalui operator `update_service.worker_upgrade` dari SHA final.
   Journal `hubify-midtrans-cutover.json` harus diblokir worker bila nonterminal.
   Jangan mengedit worker terpasang dengan patch ad hoc.
3. Package dan prebuild image app/tools melalui mekanisme resmi. Verifikasi semua
   runtime bytes terhadap manifest dan Git; prepared-image disk budget hanya
   digunakan setelah kedua image terbukti tersedia dan identik.
4. Jalur Hubify menggunakan `installer/midtrans_cutover.Native` dan state machine
   `promotions_cutover.Cutover` di bawah operation lock. Baseline khusus Hubify
   memverifikasi dua pasangan CRLF/LF historis read-only, bukan mengubah ledger.
   Jalur publik hanya menerima canonical v1.8.3 dengan signed policy
   `midtrans-snap-forward-v1` dan worker yang benar-benar memuat executor ini.
5. Hentikan timer/worker secara terkendali, tunggu maintenance/J&T aktif selesai,
   fence rute toko yang telah direview, tunggu koneksi aktif drain, stop app.
   Webhook saat maintenance menerima kegagalan retryable. Tidak ada request
   membuat/membatalkan pengiriman J&T; tiga approval Production dipertahankan.
6. Backup konsisten database, media, dan seluruh konfigurasi privat; verifikasi
   checksum, scratch restore database, ekstraksi media/config. Simpan key integrasi
   yang sama; kehilangan key membuat versi konfigurasi/token tidak dapat dibaca.
7. Jalankan Prisma migrate deploy dari tools kandidat. Periksa34→35, SQL/ledger
   historis identik, semua row hash existing sama, tabel baru kosong, full schema
   hash tepat. Migrasi hanya DDL tabel baru; FK mengambil lock singkat pada Payment
   yang sudah write-fenced. Tidak diperlukan backfill data lama.
8. Aktivasi image kandidat, readiness, metadata baseline, buka traffic, mulai ulang
   timer/updater. Verifikasi image/source/versi, halaman admin/customer, checkout,
   penolakan payload webhook tidak sah, worker dan konfigurasi J&T unchanged.
9. Baru setelah deployment dan smoke berhasil: tag annotated pada commit final,
   release dengan artefak/checksum, signed catalog/policy kompatibel. Tidak ada
   apply otomatis atau aktivasi merchant pada toko lain.

### Pemicu dan batas rollback

Sebelum migrasi: build/backup/drain/preflight gagal → state machine mengembalikan
app/compose lama bila diperlukan, dengan ledger lama tetap wajib. Jangan mengulang
aksi eksternal yang interupsinya belum diketahui; jalankan reconcile resmi setelah
memeriksa proses build/backup/migration tidak masih aktif.

Sesudah migrasi: schema mismatch, readiness gagal, snapshot berubah atau guard
berubah → tetap fence dan `recovery_required`. Executor **forward-only** setelah
migrasi. v1.8.3 secara struktural tidak memakai tabel tambahan, tetapi belum
memiliki webhook/worker Midtrans: rollback kode lama setelah Midtrans menerima
traffic dapat kehilangan rekonsiliasi gateway. Jangan otomatis rollback aplikasi
yang sudah menerima pembayaran baru; prioritaskan perbaikan forward dengan key,
attempt, inbox dan histori tetap utuh. Jika kode lama dipakai sementara sebelum
ada attempt baru, operator wajib membuktikan tabel Midtrans kosong, mempertahankan
schema35/ledger, menonaktifkan penerbitan baru dan merekam recovery terpisah;
jangan melabel ulang database sebagai schema34.

**Restore database berbeda dari rollback kode.** Restore backup hanya dengan
keputusan recovery eksplisit setelah inventaris transaksi/order baru, fencing
dan rekonsiliasi provider. Jangan otomatis mengembalikan dump lama setelah
traffic dibuka karena dapat menghapus pesanan dan klaim pembayaran baru.

Worker Midtrans dimulai independen dari pekerjaan carrier pada maintenance tick.
Lease/cooldown tersimpan; inbox webhook dan versi konfigurasi tahan restart.
Pesanan lama masih memakai worker/metode snapshot lama. Tidak ada flush cache
promosi atau perubahan harga; API pembayaran bersifat no-store. Saat provider
tidak tersedia, expiry menahan stok dan mencoba kembali; pembayaran terlambat
atau refund menjadi review, bukan membuka pesanan/refund otomatis.
